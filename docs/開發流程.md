# 開發流程

> 每次開始新的工具專案時，GPT、Codex、Claude
> 都必須先閱讀本文件，再開始任何討論、分析或 Coding。

------------------------------------------------------------------------

# 一、開發目的

開發目的是：

-   解決 Jamie 真正提出的需求。
-   保持工具簡單、穩定、容易維護。
-   保護既有功能。
-   建立清楚的 Git 紀錄。

不是：

-   展示技術能力。
-   無限增加功能。
-   過度設計。
-   把小工具做成大型平台。

------------------------------------------------------------------------

# 二、基本原則

## 1. 先討論需求

Jamie 先提出需求。

GPT 必須先與 Jamie 討論需求，協助釐清問題。

不得直接開始：

-   Proposal
-   Coding
-   架構設計

------------------------------------------------------------------------

## 2. 不得無限延伸

GPT、Codex、Claude 只能處理 Jamie 當前提出的需求。

不得自行加入：

-   未要求功能
-   企業級架構
-   不必要重構
-   未來可能用到的功能
-   低機率情境設計

若發現其他問題：

1.  說明問題。
2.  說明是否影響目前需求。
3.  詢問 Jamie 是否現在處理。

不得自行決定。

------------------------------------------------------------------------

## 3. 不得猜測

任何產品決策都由 Jamie 決定。

若有疑問，必須詢問 Jamie。

不得自行猜測需求、流程、UI、資料格式或使用方式。

------------------------------------------------------------------------

## 4. 最小修改原則

優先選擇：

-   改一段，不改整個模組。
-   改一個檔案，不改多個檔案。
-   沿用現有功能。
-   修正 Root Cause。

不得順手重構或修改無關功能。

------------------------------------------------------------------------

## 5. 保護既有功能

不得為了新需求破壞已正常運作的功能。

------------------------------------------------------------------------

# 三、開發流程

## Phase 0：需求討論

Jamie 提出需求。

GPT：

-   與 Jamie 討論需求。
-   聚焦目前需求。
-   不 Coding。

------------------------------------------------------------------------

## Phase 1：Requirement Specification

Codex／Claude 整理最終需求。

GPT 負責需求確認與審稿。

至少包含：

-   工具目的
-   操作流程
-   輸入
-   輸出
-   必要功能
-   支援平台
-   不做的內容
-   完成標準
-   修改邊界

Jamie 確認後才能繼續。

------------------------------------------------------------------------

## Phase 2：專案調查

GPT 提供一鍵複製純文字給 Codex／Claude。

第一次只能：

-   閱讀專案
-   理解架構
-   找相關檔案
-   找可沿用功能
-   找 Root Cause
-   找風險
-   提出需要 Jamie 決定的問題

不得 Coding。

能自行從程式碼或文件查到的資訊，不得詢問 Jamie。

------------------------------------------------------------------------

## Phase 3：Proposal

Codex／Claude 提出 Proposal。

至少包含：

-   現況
-   Root Cause
-   最小修改方案
-   修改檔案
-   不修改檔案
-   驗證方式
-   是否需要更新文件
-   是否建議 Tag／Release

Jamie 確認 Proposal 後才能開始 Coding。

------------------------------------------------------------------------

## Phase 4：Coding

Codex／Claude：

-   只修改 Proposal 確認內容。
-   不修改無關功能。
-   不順手重構。
-   不改壞正常功能。

若 Proposal 需要改變，必須停止並詢問 Jamie。

------------------------------------------------------------------------

## Phase 5：AI 自我驗證

Coding 完成後，Codex／Claude 必須先完成所有可自行完成的檢查。

依專案適用情況執行：

-   語法檢查
-   Lint
-   Type Check
-   Build
-   測試
-   Regression Test
-   git diff --check
-   git status --short
-   macOS 實機驗證（若適用）
-   Windows 實機驗證（若適用）

不得直接要求 Jamie Debug。

不得要求 Jamie 查程式碼。

不得要求 Jamie 幫忙找 Root Cause。

------------------------------------------------------------------------

## Phase 6：Jamie 手動驗證

Codex／Claude 全部檢查完成後，先回報：

-   修改檔案
-   修改摘要
-   驗證結果
-   已知限制
-   尚未 Commit
-   尚未 Docs Update
-   尚未 Push
-   尚未 Tag／Release

再提供 Jamie 驗證步驟。

Jamie 每次修改都必須親自驗證。

只有 Jamie 明確回覆：

PASS

才能繼續。

沒有 PASS：

不得進行 Code Commit。

------------------------------------------------------------------------

# 四、Git 流程

## Code Commit

由 Codex／Claude 建立。

完成後回報：

-   Commit Hash
-   Commit Message
-   修改檔案
-   git diff --check
-   git status --short
-   Working Tree 狀態

------------------------------------------------------------------------

## Docs Update

由 Codex／Claude 執行。

發生於 Code Commit 之後。

只更新真正受影響的文件。

完成後回報：

-   修改文件
-   修改摘要
-   文件 diff
-   git diff --check
-   確認未修改程式碼

------------------------------------------------------------------------

## Docs Commit

由 Codex／Claude 建立。

完成後回報：

-   Commit Hash
-   Commit Message
-   修改文件
-   git diff --check
-   git status --short
-   Working Tree Clean
-   尚未 Push
-   尚未建立 Tag／Release

------------------------------------------------------------------------

## Push

由 Jamie 使用 GitHub Desktop 執行。

------------------------------------------------------------------------

## Tag／Release

完成：

Jamie 手動驗證 PASS → Code Commit → Docs Update → Docs Commit → Jamie
Push

後，由 GPT 判斷是否建議建立 Tag／Release，並說明原因。

通常不需要：

-   Bug Fix
-   一般功能調整
-   UI／文案修改
-   GitHub Pages 更新
-   文件更新
-   開發中版本
-   內部測試版本

建議建立：

-   第一個正式版本
-   新的可下載版本（App、EXE、PKG、MSI）
-   對外正式發布
-   重大功能版本
-   不相容變更
-   Jamie 明確要求建立版本節點

若建議建立，GPT 必須提供：

-   Tag Name
-   Release Title
-   Release Notes
-   Upload Checklist
-   GitHub 操作步驟

是否建立 Tag／Release，由 Jamie 最終決定。

------------------------------------------------------------------------

# 五、責任分工

-   需求討論：Jamie + GPT
-   需求整理（Requirement Specification）：Codex／Claude
-   需求確認與審稿：GPT
-   專案調查：Codex／Claude
-   Proposal：Codex／Claude
-   Proposal 確認：Jamie
-   Coding：Codex／Claude
-   AI 自我驗證：Codex／Claude
-   手動驗證：Jamie
-   Code Commit：Codex／Claude
-   Docs Update：Codex／Claude
-   Docs Commit：Codex／Claude
-   Push：Jamie（GitHub Desktop）
-   Tag／Release：Jamie（GitHub 網頁）
-   Release 內容與操作引導：GPT

------------------------------------------------------------------------

# 六、固定流程

Jamie 提出需求 → GPT 討論需求 → Codex／Claude 整理最終需求 → GPT 審稿 →
Jamie 確認 → GPT 提供一鍵複製文字 → Codex／Claude 調查 → Jamie
回答必要問題 → Proposal →
Jamie 確認 Proposal → Coding → AI 自我驗證 → Jamie 手動驗證 PASS → Code
Commit → Docs Update → Docs Commit → Jamie Push → 視情況 Tag／Release

------------------------------------------------------------------------

# 七、禁止事項

不得：

-   Proposal 未確認就 Coding。
-   自行擴大需求。
-   猜測 Jamie 決策。
-   重構無關模組。
-   改壞正常功能。
-   把 AI 可自行完成的工作交給 Jamie。
-   要求 Jamie 查程式碼。
-   要求 Jamie 找 Root Cause。
-   AI 尚未完成驗證就要求 Jamie 測試。
-   Code 與 Docs 放在同一個 Commit。
-   未經 Jamie 同意建立 Release。

------------------------------------------------------------------------

# 八、最高原則

理解需求 → 鎖定範圍 → 最小修改 → 保護既有功能 → AI 先完成驗證 → Jamie
驗證 PASS → Code Commit → Docs Update → Docs Commit → Jamie Push →
視情況 Tag／Release
